# 阶段一 · 需求采访

**目标：把"我想要个好看的/能用的东西"压成一组可观察的成功判据和一份明确的不做清单。**
采访没做完之前，一行代码都不写，一个文件都不建（除了项目目录与状态文件）。

## 产出（唯一交付物）

`docs/01-需求.md`，必须含这些小节标题（门禁逐字检查）：

```markdown
# <项目名> 需求

## 一句话目标
## 用户场景（谁在什么时候用它做什么）
## 真实产物形态
## 成功判据（可观察）
## 边界：不做的事
## 依赖与凭据
## 验收环境
```

### 各小节写什么

- **一句话目标**：一句话，没有"并且"。要两个目标就是两个项目。
- **用户场景**：至少 2 条，具体到"用户在哪个界面、做什么动作、看到什么"。
- **真实产物形态**：从这几类里挑，写清楚：本地 bundle（Host 半边 / Client 半边 / 两者）、仅配置 bundle（例如接 MCP）、agent preset（模式）、对现有插件的修改。
- **成功判据（可观察）**：每条都要能被"命令输出"或"人眼看一个具体现象"证实。反例：「界面更美观了」；正例：「在 `conversation.composer.dock` 出现一个 48×48 的圆形图标，点击后计数 +1，刷新页面后计数保留」。每条判据后面留一个 `证据：` 空行，验收阶段回填。
- **边界：不做的事**：至少 3 条。这一节是防膨胀的闸门，也是审查员核对"有没有偷偷加需求"的依据。
- **依赖与凭据**：需要哪个 Service/包/外部服务；需要用户提供什么（路径、key、权限）；装什么需要完整访问权限。
- **验收环境**：在哪台机器、哪个 Profile、哪个页面、什么权限模式下验收；重启是否可接受。

## 怎么采访

- 用 `ask_user_question`，**一次最多 4 个问题**，每个问题给选项并把推荐项排第一（用户点一下就能答）。
- 一次只问一轮：拿到答案再决定要不要追问。不要一口气甩 12 个问题。
- 必须问到的是：产物形态、成功判据（至少一条真机现象）、验收环境、权限边界、不做什么、截止条件（什么情况算"先这样"）。
- 能从环境里查到的（插件的 Profile、已有 bundle、可用 Slot）**自己查**，不要问用户。
- 用户答不上来的地方，写出你的假设，并在文档里标 `（假设，需用户确认）`，然后在收口时用一次 `ask_user_question` 让用户确认这些假设。

## 这个阶段不许做的事

- 不许写插件代码、不许建 bundle、不许安装任何东西。
- 不许把"用户说想要个好看的"直接翻译成具体 Slot 名——那是阶段二查出来的东西。
- 不许把无法验证的愿望写进成功判据。
- 不许跳过"不做的事"小节（门禁会拦）。

## 收口（四步，顺序不能换）

1. 门禁：

```powershell
$PC = "$env:DSH_HOME\plugin-creator\gates\pc.mjs"
node $PC gate --stage interview --project <目录>
```

2. 派发独立审查员（用 `subagent`，只给路径，模板见 `plugin-creator`）。本轮要核对的证据清单就是 `docs/01-需求.md` 自己。审查重点让它盯：判据是否可观察、场景是否漏了、边界是否够硬、有没有未标注的假设。派发按 `plugin-creator` 的**三段写法**（规则范围 / 已证事实 / 输出分级）。
3. 处理 Finding：阻断级清零；主要/次要写进文档并交回用户确认。
4. 落快照，然后进**调研**阶段（不是设计阶段）：

```powershell
node $PC snapshot --project <目录> --stage interview
node $PC stage survey --project <目录> --note "需求已确认，去做现成插件调研"
```

（保留几版在 `init --keep` 时已经问过一次，这里不再问。）

**为什么不直接进设计**：需求一旦成形，第一个该问的问题不是"怎么实现"，而是"是不是已经有人做完了、而且做得比我马上能写的更好"。这个问题由下一阶段（`pc-stage-1b-survey`）带着三条可复算的检索记录来回答；绕过它直接画设计，等于替宿主把"买现成的"这条路先封死了。
