# 阶段三 · 拆计划

**目标：把设计切成"一次改动 + 一条验收命令"的原子任务，而且第一个任务一定能把东西装上。**

## 产出

`docs/03-计划.md`，任务清单必须是这种形式（门禁检查 `- [ ]` 与 `验收：`）：

```markdown
# <项目名> 计划

## 依赖与顺序
## 任务清单

- [ ] T1 最小可装可用版本：bundle 骨架 + 空 apply + 补丁行
      产物：package.json、cordis.patch.yml、index.js
      验收：plugin_manager install_bundle 返回 applied，且
            node $PC verify-install --name <包名> --target <目录> 退出码 0
      审查：需要（第一轮必须派人审）
- [ ] T2 …
      产物：…
      验收：…
      审查：需要 / 不需要（写明理由）
```

## 拆任务的标准

- **粒度**：一个任务 = 一次能验收的改动。一个任务里不要塞"写完功能 + 顺手改样式"。
- **每个任务必须有 `验收：`**，内容是可执行命令（能看退出码/输出）或明确的可观察现象。写不出验收的任务不是任务，是愿望——删掉或退回设计阶段。
- **第一个任务永远是最小可装可用版本**：能安装、能出现、能被 `verify-install` 核对。先有"装上了"，再谈"好看了"。
- **依赖顺序**：把"后面任务需要的前置接口/安装态"排在前面；每一行写清它依赖哪一条。
- **审查标记**：每个任务都要写 `审查：需要/不需要` + 理由。凡是改动**行为**、**补丁/json/yml 结构**、**安装形态**、**用户可见结果**的任务，一律写"需要"。
- **一次只推进一个任务**：清单是顺序执行的，不许并行改两个任务的文件（否则冻结核对必然报"文件被动过"）。

## 这个阶段不许做的事

- 不许出现没有验收命令的任务。
- 不许出现"优化""美化""顺便重构"这类无验收任务（要么给它一条验收，要么删掉）。
- 不许把任务拆得小到"改一个变量"（那是操作的粒度，不是验收的粒度）。
- 不许在计划里偷偷扩大阶段一定下的范围；要扩大就回阶段一/二改文档。

## 收口

```powershell
$PC = "$env:DSH_HOME\plugin-creator\gates\pc.mjs"
node $PC gate --stage plan --project <目录>
```

派发独立审查员（`subagent`，只给路径：`docs/03-计划.md`、`docs/02-设计.md`、`docs/01-需求.md`；按 `plugin-creator` 的**三段写法**：规则范围 / 已证事实 / 输出分级）。重点让它核对：**每条验收是否真的能执行**、任务是否覆盖了全部成功判据、有没有"不可验收"的活、第一条是否是最小可装版本、审查标记是否漏。

然后：

```powershell
node $PC snapshot --project <目录> --stage plan
node $PC stage develop --project <目录> --note "计划已定，进入开发"
```

（`--keep` 不用写：保留策略在项目创建时已经约定好，这里不重复问。）
